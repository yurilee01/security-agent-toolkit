### 문제 2-1 · 알림 A 확인 — 서버 두 대로 열려 있는지 재고, 설정 값 · 비밀번호 · 실행 사용자까지 점검하기

- (가) `docker ps` 의 `PORTS` 열에서 두 서버가 각각 어떻게 나왔는지 적어 주세요.
  - 쓸 내용: ① closed-web-8081 의 PORTS 값 ② open-web-8082 의 PORTS 값
  - 답:
 closed-web-8081: 127.0.0.1:8081->80/tcp
  open-web-8082: 0.0.0.0:8082->80/tcp, [::]:8082->80/tcp
- (나) 🔍 `내주소` 로 접속했을 때 `closed-web-8081` 과 `open-web-8082` 의 결과(응답 번호)를 각각 적어 주세요.
  - 쓸 내용: ① closed-web-8081 의 응답 번호 ② open-web-8082 의 응답 번호
  - 답:
  8081 포트: 000 — 접속 실패
  8082 포트: 200 — 접속 성공
  7.0.0.1:8081로 접속했을 때는 200이 나왔다.
- (다) 🔍 `closed-web-8081` 은 `127.0.0.1` 로 접속하면 열려 있는데 `내주소` 로는 거부되는 이유는 무엇인가요? 다른 PC가 접속하는 경우와 어떻게 같은가요?
  - 쓸 내용: ① 127.0.0.1 로는 열리는 이유 ② 내주소로는 거부되는 이유 ③ 다른 PC
  답:8081은 127.0.0.1로만 연결했기 때문에 내 컴퓨터 내부에서만 접속할 수 있다. 다른 PC에서 내 컴퓨터의 IP 주소로 접속해도 연결되지 않는다.
- (라) 🔍 사내 PC에서 접속되면 안 되는 관리용 서버를 켠다면 `-p` 를 어떻게 쓰고, 이것이 4일 차의 어떤 원칙과 같은가요?
  - 쓸 내용: ① -p 에 쓸 형태 ② 같은 생각을 말하는 4일 차 원칙
  - 답:-p 127.0.0.1:포트:80으로 설정해서 내 컴퓨터 내부에서만 접속할 수 있게 한다. 이는 필요한 곳에서만 접근을 허용하는 최소권한 원칙과 연결된다.
- (마) 🔍 `docker inspect` 결과에서 두 서버의 `HostIp` 는 각각 무엇이고, `PORTS` 열의 어느 표시와 같은 뜻인가요?
  - 쓸 내용: ① closed-web-8081 의 HostIp ② open-web-8082 의 HostIp ③ 각각 `PORTS` 열의 어느 표시와 같은 뜻인지
  - 답:closed-web-8081: 127.0.0.1 — PORTS의 127.0.0.1:8081->80/tcp와 같은 뜻이다.
open-web-8082: 빈 값 — 특정 IP 주소로 제한하지 않았으며, PORTS의 0.0.0.0:8082->80/tcp와 같은 뜻이다.
- (바) 🔍 `open-web-8082` 의 비밀번호가 `docker exec` 로 그대로 읽혔습니다. 왜 문제이고, 비밀번호를 환경변수에 넣을 때 어떻게 다뤄야 하나요?
  - 쓸 내용: ① 읽힌 값 ② 왜 문제인지 ③ 다룰 때 지킬 것 두 가지 이상
  - 답:
  docker exec로 DB_PASSWORD=dev-pass-1234가 그대로 확인됐다. 컨테이너에 접근할 수 있는 사람이 비밀번호를 읽을 수 있으므로 위험하다. 실제 서비스에서는 비밀 관리 도구를 사용하고 비밀번호에 접근할 수 있는 권한을 제한해야 한다.
- (사) 🔍 `whoami` 결과는 무엇이고, 이 서버가 침해되면 왜 위험이 커지나요? 6일 차 최소권한과 어떻게 이어지나요?
  - 쓸 내용: ① whoami 결과 ② 위험이 커지는 이유 ③ 최소권한과 이어지는 점
  - 답:
  whoami 결과는 root였다. root는 관리자 권한을 가진 사용자이므로 서버가 침해되면 공격자가 파일을 수정하거나 설정을 변경하는 등 큰 피해를 줄 수 있다. 따라서 서비스는 꼭 필요한 권한만 가진 사용자로 실행해야 한다. 이는 6일 차에 배운 최소권한 원칙과 연결된다.

위험성: 컨테이너가 웹 취약점 등으로 침해(RCE)될 경우 공격자가 곧바로 root 권한을 쥐게 되며, 컨테이너 탈출(Container Escape) 시도나 시스템 전체 위협으로 이어질 가능성이 커집니다.

최소권한 원칙 연관성: 6일 차에서 강조한 최소 권한 원칙(Principle of Least Privilege)에 따라, 불필요하게 root 사용자로 구동하지 않고 별도의 일반 사용자 계정(non-root user)을 생성 및 지정하여 실행해야 합니다

### 문제 2-2 · 알림 B · C 확인 — 응답이 없는 서버와 연달아 남은 404 읽기

- (가) 🔍 `wrongport-web-8084` 가 `Up` 인데 응답이 `000` 인 원인은 무엇인가요? `PORTS` 값, `docker logs` 에 요청 줄이 있었는지, `compare-web-8085` 와 비교한 결과를 근거로 적어 주세요.
  - 쓸 내용: ① 원인 ② `PORTS` 값 ③ `docker logs` 에 요청 줄이 있었는지 ④ `compare-web-8085` 와 비교한 결과
  - 답:
  ① 원인: wrongport-web-8084는 컨테이너가 실행 중인 Up 상태였지만, nginx가 사용하는 포트와 연결한 포트가 달라서 접속에 실패했다.

② PORTS 값: 0.0.0.0:8084->8080/tcp로 표시되었다. 컨테이너 내부 8080번 포트로 연결했지만 nginx는 기본적으로 80번 포트를 사용한다.

③ docker logs 확인: nginx 시작 로그는 있었지만 GET 요청 기록은 없었다.

④ compare-web-8085와 비교: 8085->80으로 올바르게 연결한 서버는 HTTP 응답이 200이었고, 로그에도 GET / HTTP/1.1과 200이 기록되었다. 따라서 원인은 포트 설정 오류라고 판단했다.
- (나) 🔍 `probe-web-8087` 의 접속 기록은 장애 · 위협 · 접근통제 중 무엇인가요? 출처 · 시각 · 경로 · 프로그램 중 세 가지 이상을 근거로 적고, 10/19(월)의 `favicon.ico` `404` 와 무엇이 다른지 적어 주세요.
  - 쓸 내용: ① 유형 ② 근거 세 가지 이상 ③ `favicon.ico` 404 와의 차이
  - 답:
  probe-web-8087의 기록은 장애보다는 의심스러운 위협 또는 정찰 시도 가능성으로 판단했다.

근거는 다음과 같다.

출처: 172.17.0.1

시각: 10월 21일 02:55:46~02:56:27 (UTC)

경로: /admin, /login, /.env, /wp-login.php, /backup.zip을 연속으로 요청했다.

프로그램: curl/8.21.0

응답 번호: 위 경로 5개는 모두 404였고, /index.html은 200이었다.

10/19(월)의 favicon.ico 404는 브라우저가 웹사이트 아이콘을 요청했지만 파일이 없을 때도 발생할 수 있다. 반면 이번 기록은 관리자 페이지와 설정 파일, 백업 파일 등 여러 경로를 연속으로 확인했다는 차이가 있다. 다만 기록만으로 실제 공격이라고 확정할 수는 없다.
